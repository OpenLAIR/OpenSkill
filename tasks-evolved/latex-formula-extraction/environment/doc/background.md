# Comprehensive Guide to Extracting Standalone LaTeX Formulas from Academic PDFs Using Python

**Key Points:**
*   Extraction of standalone mathematical formulas from academic PDFs requires a multi-stage pipeline involving Optical Character Recognition (OCR), layout analysis, and syntactic validation.
*   The `marker-pdf` library (version 1.3.3) provides a robust foundation for this task, leveraging the Surya OCR suite and the `texify` model to convert rendered equations into LaTeX strings.
*   Mathematical regions are highly prone to OCR artifacts; therefore, secondary validation using Abstract Syntax Tree (AST) parsers like `pylatexenc` is strongly recommended.
*   Visual rendering verification via headless browsers (e.g., Playwright) equipped with MathJax offers the highest confidence in formula integrity.
*   Alternative approaches, such as `PyMuPDF` block dictionary extraction, provide crucial bounding box data that pure OCR pipelines sometimes misinterpret.

**Technical Feasibility and Constraints:**
Research suggests that while modern deep learning pipelines have drastically improved PDF-to-Markdown conversion, perfectly extracting 100% of mathematical equations remains elusive due to the complex, non-standardized nature of PDF encoding. It seems likely that a hybrid approach—combining structural PDF parsing with vision-based OCR—yields the most reliable results. The evidence leans toward an architecture where `marker-pdf` handles the initial transcription, followed by rigorous programmatic sanitization to strip artifacts (such as equation numbers and trailing punctuation) and ensure balanced LaTeX syntax.

**Overview of the Proposed Pipeline:**
To build a reusable, production-grade Python utility for LaTeX formula extraction, developers must navigate a labyrinth of deep learning models, regex heuristics, and browser-based rendering checks. This report details the precise API implementations, configuration parameters, and error-handling strategies required to construct such a system, specifically utilizing `marker-pdf` v1.3.3, `pylatexenc`, Playwright, and `PyMuPDF`.

## 1. The Marker-PDF (Version 1.3.3) Framework

The `marker-pdf` library, maintained by Datalab, has emerged as a premier open-source utility for converting complex academic documents into structured Markdown [cite: 1, 2]. Unlike basic text extractors, `marker-pdf` utilizes a deep learning pipeline to infer document layout and parse mathematical equations [cite: 2, 3].

### 1.1 Python API Usage for Version 1.3.3

In version 1.3.3, the API relies heavily on object-oriented converters rather than the standalone function calls seen in earlier 0.x versions [cite: 2, 3]. The core entity is the `PdfConverter` class, which manages the pipeline of providers, builders, processors, and renderers [cite: 2].

#### Exact Import Paths and Function Signatures

To execute a PDF-to-Markdown conversion programmatically in Python, the following imports and setup are required [cite: 1, 2]:

```python
import os
from marker.converters.pdf import PdfConverter
from marker.models import create_model_dict
from marker.output import text_from_rendered

def extract_markdown_from_pdf(pdf_path: str) -> str:
    """
    Converts a PDF file to Markdown using marker-pdf 1.3.3.
    
    Args:
        pdf_path (str): The absolute or relative path to the academic PDF.
        
    Returns:
        str: The fully formatted Markdown text containing LaTeX equations.
    """
    # 1. Initialize the dictionary of deep learning models (Surya, Texify, etc.)
    # This automatically downloads and caches weights to your local HuggingFace directory.
    model_dict = create_model_dict()
    
    # 2. Instantiate the PdfConverter with the required models
    converter = PdfConverter(artifact_dict=model_dict)
    
    # 3. Render the PDF into a Pydantic BaseModel
    rendered_document = converter(pdf_path)
    
    # 4. Extract the raw Markdown text from the rendered object
    text, metadata, images = text_from_rendered(rendered_document)
    
    return text

if __name__ == "__main__":
    markdown_output = extract_markdown_from_pdf("sample_research_paper.pdf")
    print(markdown_output)
```

**Understanding the Output Structure:**
The output generated by `text_from_rendered` provides the raw Markdown string [cite: 2]. Within this string, `marker-pdf` enforces a strict mathematical delimiter convention:
*   **Display Math (Standalone/Block):** Represented using double dollar signs (`$$ ... $$`) [cite: 1, 2].
*   **Inline Math:** Represented using single dollar signs (`$ ... $`) [cite: 1, 4].

The library does *not* natively output the `\[ ... \]` or `\( ... \)` notations for math blocks, strongly preferring the GitHub-flavored Markdown dollar-sign syntax [cite: 2, 5].

### 1.2 Configuration Options for Maximizing Extraction Quality

To maximize the quality of LaTeX extraction, particularly for standalone formulas, several configuration flags and environment variables must be finely tuned. By default, `marker-pdf` attempts to extract text directly from the PDF streams to save computational resources, relying on OCR only heuristically [cite: 3, 6]. However, digital text streams often scramble mathematical symbols. 

To override this and force high-fidelity visual transcription, the following configurations are vital [cite: 2, 7]:

| Parameter / Env Variable | Purpose in Formula Extraction | Recommendation |
| :--- | :--- | :--- |
| `TORCH_DEVICE` | Determines hardware acceleration (`cuda`, `mps`, `cpu`) [cite: 2, 8]. | Set to `cuda` or `mps`. CPU inference for math models is exceedingly slow [cite: 1]. |
| `--force_ocr` (CLI) / config dict | Forces OCR processing on the entire document, overriding embedded digital text [cite: 2, 7]. | **Highly Recommended**. Ensures inline and display math are passed to the `texify` model rather than relying on corrupted PDF character maps [cite: 2, 7]. |
| `--strip_existing_ocr` | Removes invisible OCR layers that may confuse the layout engine [cite: 2, 7]. | Enable if processing older, previously scanned papers [cite: 7]. |
| `--use_llm` | Integrates a Large Language Model (e.g., Gemini-2.0-flash) for post-processing and artifact correction [cite: 2, 7]. | **Recommended**. Drastically improves multi-line alignment and complex matrix formatting [cite: 2, 7]. |
| `--redo_inline_math` | Specifically forces the pipeline to re-evaluate and re-OCR inline mathematical spans [cite: 2, 7]. | Essential if the distinction between inline text and math variables is critical [cite: 7]. |

#### Programmatic Implementation of Configurations

When using the Python API, these settings can be passed via the `marker.config.parser.ConfigParser` or managed via environment variables [cite: 6, 9]:

```python
import os
from marker.config.parser import ConfigParser
from marker.converters.pdf import PdfConverter
from marker.models import create_model_dict
from marker.output import text_from_rendered

# Set environment variables for hardware acceleration
os.environ["TORCH_DEVICE"] = "cuda" # or "mps" for Apple Silicon
os.environ["INFERENCE_RAM"] = "16"  # Adjust based on VRAM

def extract_high_quality_math(pdf_path: str):
    config_dict = {
        "force_ocr": True,           # Force visual math recognition
        "strip_existing_ocr": True,  # Remove legacy text layers
        "use_llm": True,             # LLM post-processing for equations
        "redo_inline_math": True     # Improve inline math accuracy
    }
    
    config_parser = ConfigParser(config_dict)
    
    converter = PdfConverter(
        artifact_dict=create_model_dict(),
        config=config_parser.generate_config_dict()
    )
    
    rendered = converter(pdf_path)
    text, _, _ = text_from_rendered(rendered)
    return text
```

### 1.3 Handling Multi-line Equations and Known Limitations

**Multi-line and Aligned Environments:**
When processing equations that span multiple lines (e.g., `\begin{align} ... \end{align}`), `marker-pdf` attempts to preserve the alignment characters (`&`) and line breaks (`\\`). However, due to the nature of bounding box detection, a common failure mode is splitting a single multi-line equation array into multiple, distinct `$$...$$` blocks [cite: 3, 10]. 

**Numbered Equations:**
Academic papers frequently number display equations at the right margin (e.g., `(1.1)`). `marker-pdf` often includes these tags *inside* the LaTeX string (e.g., `$$ f(x) = y \tag{1.1} $$` or simply raw text `$$ f(x) = y (1.1) $$`) [cite: 11, 12]. This requires aggressive post-processing to strip out numbering if pure mathematical evaluation is the goal.

**Known Limitations of marker-pdf (v1.3.3):**
1.  **Imperfect Conversion Rate:** As explicitly stated in the documentation, `marker-pdf` will not convert 100% of equations to LaTeX [cite: 3, 10]. 
2.  **Whitespace and Indentation:** Horizontal spacing within formulas (e.g., `\quad`, `\hspace`) is rarely preserved perfectly [cite: 3, 10].
3.  **Column Misclassification:** In double-column formats, large equations spanning both columns may break the reading order, resulting in fragmented equations [cite: 13, 14].

## 2. Surya OCR Models and the Texify Pipeline

The power of `marker-pdf` lies in its orchestrated use of multiple distinct deep learning models, collectively known as the Surya OCR suite, alongside the `texify` model [cite: 1, 15].

### 2.1 The Ensemble of Models

The pipeline operates in a highly specific sequence [cite: 3, 13, 14]:

1.  **`surya_layout` (datalab-to/surya_layout):** This model segments the document page into semantic blocks (e.g., Title, Text, Table, Figure, Equation) [cite: 14, 16]. It is responsible for identifying the bounding boxes of standalone mathematical formulas.
2.  **`surya_det3` (vikp/surya_det3):** A text detection model that identifies the precise boundaries of text lines within the semantic blocks [cite: 15, 16].
3.  **`surya_rec2` (vikp/surya_rec2):** The primary OCR recognition engine. It is used for standard alphanumeric text but is generally bypassed or supplemented for mathematical blocks [cite: 15, 16].
4.  **`texify` (datalab-to/texify) / `surya_latex_ocr`:** This is a highly specialized model built on the Donut architecture (an end-to-end vision-to-text transformer) [cite: 14, 17]. When `surya_layout` flags a bounding box as an equation, the image crop of that region is sent to `texify` to generate the raw LaTeX string [cite: 5, 18].
5.  **`surya_tablerec` / `surya_tablerec`:** Utilized specifically for parsing grid structures, though occasionally invoked if a matrix is misclassified as a table [cite: 16].

### 2.2 The Role and Limitations of the `texify` Model

The `texify` model is the absolute core of the formula extraction capability. Trained on the `im2latex` dataset and paired web equations across 4x A6000 GPUs, it is optimized to output Markdown and LaTeX simultaneously [cite: 5, 17].

**Known Accuracy Issues and Misrecognitions:**
*   **Resolution Constraints:** `texify` was predominantly trained on 96 DPI images with a maximum resolution of 420x420 pixels [cite: 5]. Extremely wide equations (e.g., long Taylor series expansions) or very tall arrays are prone to hallucination or truncation [cite: 5].
*   **Single-Character Instability:** The model performs poorly on single-letter isolated images (e.g., a standalone variable $x$ on a line), sometimes yielding worse Character Error Rates (CER) than older models like `Latex-OCR` for minimal inputs [cite: 19, 20].
*   **Cropping Sensitivity:** If the upstream `surya_layout` model provides a bounding box that clips the top of a superscript or the bottom of a subscript, `texify` will fail gracefully but incorrectly, producing broken LaTeX [cite: 5].

**Control Parameters:**
While the `texify` standalone repository supported a `TEMPERATURE` setting to control generation diversity (lower temperature = less hallucination), this is abstracted away in the `marker-pdf` high-level API [cite: 5]. To manipulate this, one must intercept the model initialization or use the `--use_llm` flag to correct hallucinations programmatically [cite: 7]. Note that Datalab states that the standalone `texify` has been deprecated and its capabilities rolled directly into the main `surya` library via the `surya_latex_ocr` command [cite: 5].

## 3. Distinguishing Display Math from Inline Math

Once the `marker-pdf` pipeline yields a Markdown string, the next critical step is extracting the standalone formulas. 

### 3.1 Patterns and Heuristics for Extraction

In `marker-pdf` output, display math is fenced by `$$` on either side [cite: 1, 2]. However, a naive regex like `\$\$(.*?)\$\$` is insufficient because:
1.  Formulas often contain internal line breaks (`\n`).
2.  Adjacent inline math formulas (e.g., `$x$` and `$y$`) might accidentally trigger false positive matches if regex greediness is not controlled.
3.  Some block formulas are mistakenly formatted by OCR with single dollars but reside on their own isolated lines.

**The Optimal Regex for Marker-PDF Block Math:**

```python
import re

def extract_display_math(markdown_text: str) -> list[str]:
    """
    Extracts standalone block math from marker-pdf markdown output.
    """
    # Pattern explanation:
    # \$\$          : Match opening $$
    # ([\s\S]*?)    : Match any character (including newlines) non-greedily
    # \$\$          : Match closing $$
    # (?:\s*$)      : Ensure it is essentially standalone by looking for line ends/whitespace
    
    pattern = re.compile(r'\$\$([\s\S]*?)\$\$', re.MULTILINE)
    
    raw_formulas = pattern.findall(markdown_text)
    
    # Clean up whitespace
    return [formula.strip() for formula in raw_formulas]
```

### 3.2 Standard Environments and Delimiters in Source LaTeX

In traditional LaTeX source code, displayed equations can be invoked using numerous environments. If you are parsing raw LaTeX or if `marker-pdf` occasionally leaks native environments without the `$$` wrapper, you must account for all of them [cite: 11].

The standard display math delimiters and environments include:
*   **Delimiters:** `$$ ... $$`, `\[ ... \]` [cite: 11, 12].
*   **Base Environments:** `\begin{equation} ... \end{equation}`, `\begin{displaymath} ... \end{displaymath}` [cite: 11].
*   **AMS-Math Environments:** `\begin{align}`, `\begin{gather}`, `\begin{multline}`, `\begin{flalign}`, `\begin{eqnarray}` (and their starred versions like `\begin{align*}`) [cite: 11].

### 3.3 Normalization to `$$...$$` Format

If `marker-pdf` extracts an equation preserving its `\begin{align}` syntax inside the `$$...$$`, it can cause double-rendering issues in certain markdown viewers [cite: 4, 21]. Conversely, if you want to enforce pure `$$...$$` wrappers around raw AMS-Math environments extracted from other sources, you need a robust normalization function.

```python
def normalize_to_block_math(formula: str) -> str:
    """
    Normalizes various LaTeX display math environments into a clean $$ ... $$ block.
    Preserves structural environments (like aligned, matrix) inside the block.
    """
    # Remove outer \[ \]
    formula = re.sub(r'^\\\[(.*?)\\\]$', r'\1', formula, flags=re.DOTALL).strip()
    
    # List of environments that inherently trigger display mode but might need 
    # internalizing into a $$ block for markdown compatibility.
    display_envs = [
        'equation', 'equation*', 'align', 'align*', 'gather', 'gather*',
        'multline', 'multline*', 'eqnarray', 'eqnarray*'
    ]
    
    for env in display_envs:
        # If the formula is perfectly wrapped in an environment
        env_pattern = rf'^\\begin{{{env}}}(.*?)\\end{{{env}}}$'
        match = re.search(env_pattern, formula, re.DOTALL)
        if match:
            inner_content = match.group(1).strip()
            
            # Convert structural alignments into 'aligned' inside $$
            if 'align' in env:
                return f"$$ \\begin{{aligned}} {inner_content} \\end{{aligned}} $$"
            elif 'gather' in env:
                return f"$$ \\begin{{gathered}} {inner_content} \\end{{gathered}} $$"
            else:
                return f"$$ {inner_content} $$"
                
    # If no specific environment was found, just wrap it
    if not formula.startswith("$$"):
        return f"$$ {formula} $$"
    
    return formula
```

## 4. LaTeX Formula Cleaning and Validation

Due to the stochastic nature of machine learning, OCR-extracted LaTeX is riddled with structural artifacts. Attempting to feed these directly into a downstream analytical engine or RAG pipeline will lead to catastrophic failures.

### 4.1 Common OCR Artifacts in Mathematical LaTeX

1.  **Misrecognized Symbols:** Confusion between `l`, `1`, `I`, and `|`. Confusion between `\times` and `x`.
2.  **Broken Commands:** `\fiac` instead of `\frac`, `\sqit` instead of `\sqrt`.
3.  **Unmatched Brackets:** e.g., `\frac{a}{b` or `\left( x + y \right.` [cite: 22, 23].
4.  **Trailing Equation Numbers:** Extraction of visual numbering as part of the equation, e.g., `a^2 + b^2 = c^2 \quad (1.4)` [cite: 11, 12].

### 4.2 Programmatic Validation using `pylatexenc`

To validate LaTeX syntactically, regular expressions are computationally insufficient due to the recursive, nested nature of LaTeX groups (braces) [cite: 24]. The `pylatexenc` library, specifically the `pylatexenc.latexwalker` module, provides an API to parse a chunk of LaTeX into an Abstract Syntax Tree (AST) of nodes [cite: 25, 26]. 

#### Exact Import Paths and Function Signatures for `pylatexenc`

```python
from pylatexenc.latexwalker import (
    LatexWalker, 
    LatexWalkerParseError,
    LatexMacroNode, 
    LatexGroupNode, 
    LatexCharsNode
)
```

The `LatexWalker` class takes a string and attempts to parse it [cite: 22, 26]. 

*   `LatexWalker(s, macro_dict=None, **flags)` [cite: 22].
*   Critical Flags:
    *   `tolerant_parsing=True|False`: If `False`, the parser raises an exception on syntax errors (ideal for strict validation) [cite: 22, 26].
    *   `strict_braces=True|False`: Requires braces to match perfectly [cite: 22, 26].

#### Validation and Brace Checking Implementation

```python
def validate_latex_syntax(latex_str: str) -> bool:
    """
    Uses pylatexenc to strictly validate the structural integrity of a LaTeX string.
    Checks for balanced braces and valid macro structures.
    """
    # Strip the $$ markers for validation
    core_latex = latex_str.strip('$ \n')
    
    try:
        # Initialize the walker with strict parsing to catch unmatched braces
        walker = LatexWalker(core_latex, tolerant_parsing=False)
        
        # Parse the entire string. If it completes without raising LatexWalkerParseError, 
        # the brace matching and macro syntax are structurally sound.
        nodes, pos, length = walker.get_latex_nodes()
        return True
        
    except LatexWalkerParseError as e:
        print(f"Validation failed at position {e.pos}: {e.msg}")
        return False
```

### 4.3 Detecting and Fixing Common Syntax Errors

While `LatexWalker` detects errors [cite: 26], automatically fixing them requires heuristic interventions. 

**Fixing Unmatched `\left` and `\right`:**
LaTeX requires every `\left<delim>` to have a corresponding `\right<delim>` (or `\right.`). OCR often drops one.

```python
def fix_left_right_delimiters(formula: str) -> str:
    """
    Heuristically balances \left and \right operators.
    """
    left_count = len(re.findall(r'\\left\b', formula))
    right_count = len(re.findall(r'\\right\b', formula))
    
    if left_count > right_count:
        # Append invisible right delimiters to close the groups
        formula += " \\right." * (left_count - right_count)
    elif right_count > left_count:
        # Prepend invisible left delimiters
        formula = ("\\left. " * (right_count - left_count)) + formula
        
    return formula
```

**Stripping Trailing Equation Numbers:**
Academic equations extracted by `texify` frequently include the numbering string [cite: 11, 12]. This regex safely removes trailing identifiers like `(1)`, `(2.3a)`, `[cite: 2]`, or explicit `\tag{...}` commands [cite: 12].

```python
def strip_equation_numbering(formula: str) -> str:
    """
    Removes visual equation numbering and \tag{} macros.
    """
    # Remove standard LaTeX tagging macros
    formula = re.sub(r'\\tag\{.*?\}', '', formula)
    formula = re.sub(r'\\label\{.*?\}', '', formula)
    formula = re.sub(r'\\nonumber\b', '', formula)
    formula = re.sub(r'\\notag\b', '', formula)
    
    # Remove right-aligned numbering like (1), (A.1), [3.4] at the end of the string
    # E.g., Matches: " \quad (1.2) $$" -> " $$"
    pattern = r'(?:\s*|\\quad\s*|\\qquad\s*)[(\[]?[a-zA-Z0-9]+(?:\.[a-zA-Z0-9]+)*[)\]]?\s*$'
    formula = re.sub(pattern, '', formula).strip()
    
    # Clean up trailing punctuation accidentally included in the math block
    formula = re.sub(r'[,.;:]\s*$', '', formula)
    
    return formula
```

## 5. Rendering Verification with Playwright

Even if a formula passes AST validation via `pylatexenc` [cite: 26], the ultimate test of its accuracy is whether an engine like MathJax can successfully render it into a DOM tree without throwing an internal rendering error [cite: 27].

By utilizing Playwright (version 1.57.0) in a headless Chromium instance, we can inject the extracted LaTeX into a minimal HTML document, allow MathJax to process it, and dynamically poll the DOM for error classes such as `.MathJax_ERROR` or `<mjx-merror>` [cite: 27].

### 5.1 Playwright Implementation for MathJax Verification

This script utilizes `sync_playwright` to orchestrate the headless browser, injecting a local HTML template equipped with the MathJax CDN [cite: 27, 28].

```python
import time
from playwright.sync_api import sync_playwright

class MathJaxVerifier:
    def __init__(self):
        self.playwright = sync_playwright().start()
        self.browser = self.playwright.chromium.launch(headless=True) # Ensure headless execution
        self.page = self.browser.new_page()
        
    def close(self):
        """Cleanly terminate the browser context."""
        self.browser.close()
        self.playwright.stop()

    def verify_formula(self, latex_string: str) -> dict:
        """
        Injects a LaTeX formula into a DOM with MathJax and checks for rendering errors.
        """
        # Minimal HTML template loading MathJax 3 via CDN
        # Using double braces {{ }} to escape Python's f-string formatting
        html_content = f"""
        <!DOCTYPE html>
        <html>
        <head>
            <meta charset="UTF-8">
            <script>
                window.MathJax = {{
                    tex: {{
                        inlineMath: [['$', '$']],
                        displayMath: [['$$', '$$']]
                    }},
                    startup: {{
                        pageReady: () => {{
                            return MathJax.startup.defaultPageReady().then(() => {{
                                window.renderingComplete = true;
                            }});
                        }}
                    }}
                }};
            </script>
            <script id="MathJax-script" async 
                src="https://cdn.jsdelivr.net/npm/mathjax@3/es5/tex-chtml.js">
            </script>
        </head>
        <body>
            <!-- Inject the raw LaTeX block -->
            <div id="formula-container">$$ {latex_string} $$</div>
        </body>
        </html>
        """
        
        # Load the HTML content directly into the page
        self.page.set_content(html_content)
        
        # Wait for the MathJax promise to resolve indicating processing is done
        try:
            self.page.wait_for_function("window.renderingComplete === true", timeout=5000)
        except Exception as e:
            return {"valid": False, "error": "MathJax rendering timed out."}
            
        # Execute JavaScript in the browser to query for MathJax error nodes
        # mjx-merror is used in MathJax v3, .MathJax_ERROR in legacy versions
        verification_result = self.page.evaluate("""
            () => {
                const container = document.querySelector('#formula-container');
                
                // MathJax v3 error element
                const merror = container.querySelector('mjx-merror');
                if (merror) {
                    return { valid: false, error: merror.textContent || "Unknown mjx-merror" };
                }
                
                // Fallback for older MathJax versions
                const legacyError = container.querySelector('.MathJax_Error');
                if (legacyError) {
                    return { valid: false, error: legacyError.textContent };
                }
                
                return { valid: true, error: null };
            }
        """)
        
        return verification_result

# Example Usage
if __name__ == "__main__":
    verifier = MathJaxVerifier()
    
    # Valid formula test
    res = verifier.verify_formula(r"\frac{-b \pm \sqrt{b^2 - 4ac}}{2a}")
    print("Valid test:", res)
    
    # Invalid formula test (unmatched brace)
    res = verifier.verify_formula(r"\frac{-b \pm \sqrt{b^2 - 4ac}{2a}")
    print("Invalid test:", res)
    
    verifier.close()
```

### 5.2 Handling Encoding Issues and Raw Strings

When passing LaTeX strings in Python, the backslash `\` is an escape character. If you read the output from `marker-pdf` from a file, Python handles the raw characters correctly. However, if you are defining strings manually in code or manipulating them via Regex substitutions, you must use Python raw strings (`r"\frac"`) or double-escape them (`"\\frac"`) [cite: 29]. Failure to do so will result in `\f` being interpreted as a form-feed character, which immediately breaks both `pylatexenc` and MathJax [cite: 29, 30].

## 6. Alternative and Complementary Approaches: PyMuPDF

While `marker-pdf` relies on vision models, traditional PDF parsers like `PyMuPDF` (`fitz`) process the underlying PDF structural data. A highly effective complementary approach involves using PyMuPDF to extract text blocks and identify equation regions based on structural cues (like specific font usage), which can then be used to cross-reference or bound the `marker-pdf` output [cite: 31, 32].

### 6.1 Identifying Equations via PyMuPDF Text Dictionaries

PyMuPDF's `page.get_text("dict")` method returns a highly detailed JSON-like structure of the PDF page, nested as `blocks -> lines -> spans` [cite: 32, 33]. Each span contains the specific font name and size used by the PDF renderer [cite: 33].

Mathematical formulas in PDFs compiled by LaTeX frequently utilize specific fonts, most notably the Computer Modern family (e.g., `CMMI10` for Computer Modern Math Italic) [cite: 34]. Furthermore, `PyMuPDF` assigns a specific binary flag (`flags=6`) to certain math spans [cite: 34].

```python
import pymupdf

def extract_math_bboxes(pdf_path: str, page_num: int) -> list[tuple]:
    """
    Uses PyMuPDF to analyze font properties and extract bounding boxes 
    for likely mathematical formulas on a given page.
    """
    doc = pymupdf.open(pdf_path)
    page = doc[page_num]
    
    # Extract the detailed dictionary
    data = page.get_text("dict")
    
    math_bboxes = []
    
    for block in data["blocks"]:
        # Skip image blocks
        if block["type"] != 0:
            continue
            
        block_is_math = False
        
        for line in block.get("lines", []):
            for span in line.get("spans", []):
                font_name = span.get("font", "")
                
                # Heuristic: Check if the font is a known math font
                # CMMI = Computer Modern Math Italic
                # CMSY = Computer Modern Symbol
                if "CMMI" in font_name or "CMSY" in font_name or span.get("flags") == 6:
                    block_is_math = True
                    break
            
            if block_is_math:
                break
                
        if block_is_math:
            # Append the bounding box of the entire block (x0, y0, x1, y1)
            math_bboxes.append(block["bbox"])
            
    doc.close()
    return math_bboxes
```

**Complementary Workflow:** 
If the `marker-pdf` pipeline drops an equation (a known limitation [cite: 3, 10]), the bounding boxes derived from `PyMuPDF` can be isolated, rasterized to images, and passed directly to an external math OCR tool (like an isolated instance of `surya_latex_ocr` or Mathpix) to recover the lost data.

## 7. Common Pitfalls and Migration Notes

Building a resilient pipeline requires avoiding several documented traps and version-specific behaviors.

### 7.1 Marker-PDF Version Breaking Changes
*   **1.x vs 0.x Architecture:** In `marker-pdf` versions prior to 1.0, developers relied on standalone functional calls and direct interactions with `surya` module scripts. As of version 1.3.3, the entire process has been encapsulated into the `PdfConverter` class and the provider/builder/processor paradigm [cite: 2, 3]. Older tutorials referencing `convert_single_pdf` are deprecated and will throw import errors [cite: 3, 7].
*   **Deprecation of standalone Texify:** The `texify` repository and module have been formally deprecated by Datalab; the weights and functionalities are now natively embedded within the `surya-ocr` pipeline [cite: 5]. Installing raw `texify` via pip may introduce dependency conflicts with newer `surya` distributions.

### 7.2 Matrix Alignment and Multi-line Hallucinations
When processing wide matrices (e.g., a $4 \times 4$ tensor matrix), the OCR engine frequently loses track of the alignment ampersands (`&`). The output might render as a clump of variables [cite: 5, 10].
*   **Mitigation:** The only reliable programmatic mitigation within the `marker-pdf` ecosystem is passing the `--use_llm` flag [cite: 7]. This feeds the initial, potentially garbled LaTeX into a Google Gemini model alongside the visual context, instructing the LLM to reconstruct the `&` alignments logically based on spatial layout [cite: 2, 7].

### 7.3 Ghost Text and Invisible Layers
Many academic PDFs, particularly those processed by institutional archiving systems (like JSTOR), contain invisible OCR text layers layered over scanned images [cite: 2, 7]. If `marker-pdf` reads this digital text instead of re-evaluating the image, math formulas appear as random ASCII garbage (e.g., `å∫` instead of `\int`). 
*   **Mitigation:** Always use the `--strip_existing_ocr` flag when processing archival papers to force the `surya` suite to process the document purely as a visual artifact [cite: 2, 7].

## Conclusion

Constructing a Python skill to perfectly extract standalone LaTeX formulas from PDFs is a non-trivial systems engineering challenge. By establishing `marker-pdf` 1.3.3 as the primary visual transcription engine [cite: 2, 3], utilizing `pylatexenc` for strict AST validation of the output [cite: 22], and relying on Playwright with MathJax as the ultimate rendering authority [cite: 27], developers can build a high-fidelity, automated math extraction pipeline. Supplementing this pipeline with `PyMuPDF` bounding box analytics ensures that even edge-case layouts can be successfully parsed and validated [cite: 32, 33].
